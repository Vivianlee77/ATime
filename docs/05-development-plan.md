# 开发计划与交付规范

版本：v0.1；日期：2026-11-12。下列任务均为待开发项，原型不代表采集能力已经实现。

## 1. 实施顺序与预算

先验证 Windows 状态采集和计时正确性，再做常驻外壳与统计界面，最后处理安装、升级和持续运行。按一名熟悉 C# 桌面开发的工程师估算，MVP 约 **24–34 个工作日，约 5–7 周**；这是工作量估算，不是交付日期。初次学习 WPF/Win32、硬件兼容问题和公开发布签名可能增加时间。

| 阶段 | 预算 | 可展示结果 | 进入下一阶段条件 |
| --- | --- | --- | --- |
| M0 技术验证 | 2–3 天 | 普通权限下输出前台身份、输入空闲、会话与电源状态的验证程序 | 锁屏/唤醒/初始显示状态可解释，已记录受限场景 |
| M1 计时与存储 | 6–8 天 | 可重放状态机、SQLite、双指标、崩溃恢复 | 文档 06 核心计时用例及幂等测试通过 |
| M2 常驻桌面体验 | 5–7 天 | 托盘、可拖动小窗、详情、双口径、状态反馈 | 隐藏持续采集；多显示器与基本交互通过 |
| M3 设置与数据管理 | 5–7 天 | 隐私规则、CSV、清除、自启、主题与首次运行 | 不泄露隐私应用明细；所有入口状态一致 |
| M4 发布与稳定性 | 6–9 天 | 安装包、升级备份、自动检查、真实机器验收 | 发布门槛通过，已知限制写入发行说明 |

M0 是关键决策点：若显示初始状态、现代应用身份或锁屏边界无法稳定得到，应先调整支持范围和状态提示，不用 UI 动画掩盖不确定数据。

## 3. 建议仓库结构

以下为开始实现时创建的结构；当前交付只有文档和原型。

```text
screen-time-companion/
├─ README.md
├─ docs/                          # 本次设计与开发规范
├─ prototype/index.html           # 本次界面演示
├─ src/
│  ├─ ScreenTimeCompanion.App/     # WPF UI、托盘、组合根
│  ├─ ScreenTimeCompanion.Domain/  # 状态机、规则与区间
│  ├─ ScreenTimeCompanion.Application/
│  ├─ ScreenTimeCompanion.Windows/ # Win32 P/Invoke 及采集
│  └─ ScreenTimeCompanion.Infrastructure/
├─ tests/
│  ├─ ScreenTimeCompanion.Domain.Tests/
│  └─ ScreenTimeCompanion.Integration.Tests/
├─ packaging/                     # 安装与升级脚本
├─ .github/workflows/ci.yml
├─ Directory.Packages.props
├─ global.json
└─ ScreenTimeCompanion.slnx
```

项目引用方向保持 `App → Application → Domain`；Windows/Infrastructure 实现 Application/Domain 声明的边界接口，通过 App 组合。Domain 单测不能依赖真实 HWND、机器时间和用户环境。

`global.json` 锁 SDK，NuGet 使用中央版本管理和依赖锁文件；不要在文档中把“最新版本”当可重复构建配置。提交 `.gitignore`，排除 `bin/obj`、用户数据库、WAL/SHM、日志、导出记录、个人证书、签名密钥和浏览器测试临时目录。

## 4. 工程约定

- C# nullable 开启，P/Invoke 用 SafeHandle 或等价可靠释放机制，错误码变为可测试结果类型。
- 所有持续时长以整数毫秒表示；日期范围和口径使用明确类型，避免 `double hours` 到处换算。
- 单写入队列；数据库操作参数化；取消操作和退出使用有限超时，不能死等。
- 结构化日志记录事件类型、错误码与版本，不打印前台应用切换流水和完整路径。
- 首版图表用可访问的 WPF 控件/简单柱状图即可；确定需要第三方库时再审查其维护、许可和包体成本。
- 每个修复添加能暴露原问题的计时或存储回归用例；纯样式和可逆文本修改不机械补无价值单测。
- 不把“管理员运行”作为普通应用无法识别的默认解决办法。

## 5. 构建与验证流程

建好解决方案后，基本命令按固定 SDK 执行：

```powershell
dotnet restore --locked-mode
dotnet build -c Release --no-restore
dotnet test -c Release --no-build
dotnet publish src/ScreenTimeCompanion.App/ScreenTimeCompanion.App.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=false -p:PublishTrimmed=false -o artifacts/win-x64
```

这是后续工程命令示意；当前无 `.csproj`，不能对本设计包直接运行。首次建立锁文件时先普通 restore，再提交锁文件供 CI 使用。暂不追求单文件或裁剪，先验证 WPF、托盘与原生 SQLite 依赖完整可部署。

GitHub Actions 使用支持 .NET 10 的 Windows runner；各 action 固定经核验的版本/SHA。CI 运行还原、Release 编译、确定性状态机测试、临时 SQLite 集成测试、原生 SQLite 版本检查和发布产物生成。交互式锁屏、休眠、真实焦点和多显示器测试保留真实机器验收记录，不能依赖无人值守 CI 代替。

## 6. 发布方案

内部 alpha 先提供自包含 ZIP，使用固定用户目录保存数据；beta 增加每用户安装器。安装器可采用经过许可和版本核验的成熟方案，安装至当前用户应用目录并避免要求管理员；不得把 SQLite 数据放进安装目录。

默认无后台自动更新。首版在“关于”提供用户主动打开 GitHub Releases 的入口；替换安装包升级前备份数据，禁止并行启动旧新进程。发行说明写明适用 OS、安装方法、统计口径、未覆盖情况、数据位置、版本和 SHA-256 校验值。

公开发布前配置可用的代码签名方案；签名密钥通过发布环境管理，不进入仓库。签名是否可用影响分发体验，不能在未取得证书时承诺没有系统信誉提示。未签名内部测试包如实标识，不引导关闭系统安全功能。

卸载先停止应用、移除启动项/快捷方式/安装文件；默认保留历史数据并清楚提示，提供由用户选择的“同时删除本地数据”选项。清理只针对产品已验证的数据目录。开源许可证属于作者选择，未选择前不随意放置 MIT/Apache 授权；外部依赖许可独立核查。

## 7. 风险与降级

| 风险 | 前置验证 | 可接受降级 |
| --- | --- | --- |
| 某些应用身份难解析 | DEV-01/03真实应用矩阵 | 未识别桶，记录总时长且明确限制 |
| 阅读/视频被判断空闲 | 产品说明与双指标验收 | 用户切换会话视图；不自动猜播放状态 |
| 休眠与通知遗漏 | 可重放缺口测试+真实睡眠 | 标记不连续，不补算整段 |
| 多显示器与DPI导致小窗丢失 | DEV-08热插拔和多缩放 | 自动回主工作区 |
| 数据损坏/磁盘满 | 事务、备份、故障注入 | 停止计时并告知；不覆盖旧库 |
| Windows10或远程支持成本 | 独立兼容性探索 | 不扩充首版承诺范围 |
| 初次学习C#/WPF | 完成小型采集验证再估时 | 延长预算，保持核心范围 |

后续 v0.2 可考虑分类、每应用历史删除、路径变化后的手动合并、全屏自动隐藏、阅读模式提醒和 ARM64；网站统计需要额外浏览器能力与隐私设计，不能通过偷读标题替代。云同步和团队监控另立需求，不挤入此 MVP。
